# Appointment protected-payload preparation

Status: local dormant preparation, not an encrypted appointment rollout. No production key, data, configuration, external transmission or backfill was changed. Existing appointment writers/readers remain unchanged. Migration043 adds a nullable JSONB column with basic shape checks only and is registered for the ordinary migration runner; it does not activate code.

## Contract

`appointmentPayloadService` uses the existing AES-256-GCM primitive and production dedicated-key write guard. Version1 ciphertext contains appointment, patient and provider UUIDs plus reason_for_visit, patient_notes, provider_notes, cancellation_reason and metadata. New-format reads use only the current key, not legacy fallback candidates; production reads and writes require the dedicated key. Raw encrypted rows cannot be re-encrypted from their cleared/stale legacy columns: future updates must lock, authorize, hydrate, merge, then protect. The decoder compares all three identifiers after authentication, rejects unsupported/malformed/corrupt/wrong-record payloads without plaintext fallback, and preserves legacy null/empty values only when no envelope exists. Payload snapshots are bounded to1MiB and cloned. Scheduling serialization neither decrypts nor returns clinical values; clinical serialization removes the envelope. View selection is data minimization, never an authorization grant: callers must check current account, market, role/care relationship and read audit first. Identity reassignment requires an authorized decrypt/rebind transaction, not changing foreign keys under existing ciphertext.

No production route imports the helper. There is no enable switch. The preparation does not close plaintext storage or secondary-copy gaps.

## Required tests before activation

Synthetic tests must cover every writer above, legacy/encrypted/mixed data, empty/null values, corrupt/wrong-key/wrong-record failures, current authority and admin denial, no envelopes or plaintext secondary copies, concurrent triage/notes/cancel updates, exact booking/cancellation retry, reporting equivalence, visits/FHIR read compatibility and actual interrupted/repeated browser flows. Current new codec tests and disposable-DB migration test are preparation evidence only. Before deployment qualification, test schema drift explicitly: ADD COLUMN IF NOT EXISTS does not repair a pre-existing unguarded or wrongly typed column. Clinical serializers must not receive stale narrative aliases such as triage_data from joined queries; project canonical appointment fields before decoding. No live database execution is claimed.

## Production operations needing separate approval

Confirm dedicated key custody and recovery, legacy key provenance, protected backups and restore rehearsal. Roll out compatible readers and converted writers together before any encrypted-only write. Backfill must be resumable, use current row locks/version checks, verify decrypted readback, then clear plaintext atomically; no destructive cleanup without reviewed retention/rollback policy. Once encrypted writes begin, rollback cannot use an old plaintext-only reader. Version1 has no key-id ring: key rotation requires an explicitly reviewed re-encryption/key-version migration before the old key is retired; it must not quietly enable legacy/default-key fallback. Old backups, notification/chat/event copies need their own authorized retention/remediation plan. Clinical reporting acceptance and owner deployment approval remain separate gates.

## Local operational-copy cleanup (not published)

The next local slice removes cancellation narratives from routine notifications and cancellation events while preserving the appointment record itself. Provider schedule workflow queries now select scheduling fields only; runtime query replacement and output allowlisting protect persisted historical definitions/resumed output as well as new definitions. Unexpected historical string/grouped notification payloads fail closed to an empty list. Nova appointment reminders use deterministic scheduling text and no external-model call, so neither visit reasons nor remembered profile facts enter that reminder. The cancellation bridge now handles the actual POST cancellation without emitting a false booking or replay event.

These changes prevent new copies on the covered paths; they do not delete existing notification/chat/event records, activate appointment encryption, or claim the latent Nova/bridge paths were live disclosures. Historical retention cleanup and the coordinated encryption writer/reader conversion remain separate work.

The workflow notification remains an operator scheduling summary, not per-provider delivery. Other Nova check-in paths and historical profile data are outside this slice.
